# Cemu: DSU-контроллер не переподключается к серверу — постановка задачи

> Документ для независимого изучения. Нужно проверить описанный механизм по коду, найти то, что мы упустили,
> и предложить лучшее минимальное исправление. Наша идея в конце — черновик, её можно и нужно критиковать.

## 1. Контекст

- **Cemu** — эмулятор Wii U, https://github.com/cemu-project/Cemu (C++). Локальный клон:
  `M:\00_Coding\00_Projects\Cemu`, `upstream/main` = `c717fca`. Последний релиз — 2.6.
- **DSU (Cemuhook)** — UDP-протокол, по которому внешние программы (DS4Windows, BetterJoy, MotionSource на
  Android, PhoneGyro и др.) отдают эмулятору движение и кнопки. Cemu — клиент, сервер обычно на
  `127.0.0.1:26760`.
- Протокол: клиент шлёт запросы (версия, список портов, **запрос данных по слоту 0–3**), сервер отвечает. По
  соглашению сервер шлёт данные слота, пока клиент периодически повторяет запрос данных (DS4Windows и др.
  забывают клиента, если запросов нет несколько секунд).

## 2. Симптом

1. **Cemu запущен раньше DSU-сервера** — движения в игре нет, даже когда сервер уже работает. В настройках
   управления Cemu контроллер может выглядеть подключённым.
2. **Сервер перезапущен во время игры** — движение пропадает навсегда.

В обоих случаях помогает только одно из:
- в настройках управления Cemu удалить DSU-контроллер и добавить заново («−», «+») или нажать проверку
  подключения;
- перезапустить Cemu;
- иногда — подключить/отключить любое USB-устройство.

Воспроизведение: Cemu 2.6 (или сборка `c717fca`), профиль управления с DSUController, игра с гироскопом (BotW).
Запустить Cemu → потом сервер (PhoneGyro или MotionSource) → движения нет. Или: всё работает → перезапустить
сервер → движения нет.

## 3. Известные отчёты

- **#627** (открыт с 2023-01): «DSU Controller stops working after restarting MotionSource Server» — после
  перезапуска сервера помогает только перезапуск Cemu. Свежий комментарий с тем же симптомом (Steam Controller +
  steam-gyro-for-cemuhook).
- Возможно связаны: **#1609** («Cemu 2.6 не находит телефон, Dolphin находит»), **#1936** (MotionSource не
  работает). Проверить, тот ли это механизм.

## 4. Механизм (по нашему прочтению кода — проверить)

Файлы: `src/input/api/DSU/DSUControllerProvider.cpp/.h`, `DSUController.cpp`, `src/input/InputManager.cpp`,
`src/input/emulated/EmulatedController.cpp`, `src/util/helpers/ConcurrentQueue.h`.

Cemu шлёт запрос данных только в двух случаях:
1. **Разово**, из `DSUController::connect()` → `request_pad_data(m_index)`. `connect()` вызывается при загрузке
   профиля (`DSUController::load`), при добавлении контроллера (`EmulatedController::add_controller`), из
   настроек управления (`InputSettings2.cpp`) и из `InputManager::on_device_changed` (событие Windows о смене
   устройств).
2. **После каждого полученного пакета**: в конце цикла `reader_thread` — `request_pad_data(index)`. Пока пакеты
   идут, цепочка «пакет → запрос → пакет» держит себя сама.

Таймера и повторов нет. Если первый запрос ушёл, когда сервера не было, ответа нет → следующего запроса нет →
`reader_thread` навсегда блокируется в `m_socket.receive_from` (на Windows сначала приходит ошибка от ICMP «port
unreachable», её съедает обход `first_read`, дальше — блокировка). При перезапуске сервера цепочка рвётся так же.

`writer_thread` бесконечно ждёт задания в `m_writerJobs.pop()` (у `ConcurrentQueue` нет ожидания с таймаутом).

История: до коммита `f3fecba` (#1847, май 2026, переход на SDL3) у сокета был `SO_RCVTIMEO` 200 мс «чтобы потоки
могли завершиться»; его заменили пакетом-будильником в деструкторе. Но и с таймаутом повторных запросов не было:
по ошибке поток только спал 250 мс и продолжал. То есть баг, судя по всему, существует с первого коммита.

Побочное: `is_connected(i)` смотрит на последнее полученное состояние слота и не устаревает — после пропажи
сервера Cemu продолжает считать контроллер подключённым.

## 5. Ограничения для исправления

- `CONTRIBUTING.md` Cemu: код пишет и понимает человек; ИИ — для анализа, проектирования, ревью. Поэтому нужно
  минимальное исправление, которое человек наберёт и объяснит построчно.
- `CODING_STYLE.md`: новые поля `m_camelCase`, функции `CamelCase`, типы `uint32`/`sint32`, скобки на отдельных
  строках, табы. Не переформатировать чужой код.
- Работать на Windows, Linux и macOS. Не полагаться на ICMP-ошибки и `SO_RCVTIMEO` с синхронными операциями
  boost::asio (на POSIX поведение ненадёжно; таймаут недавно сознательно убрали).
- Не ломать работающий поток: при живом сервере — ни лишних запросов, ни задержек.
- Не трогать другие API ввода. Потоки: состояние слота защищено `m_mutex[index]`.
- Не пересекаться с другими нашими PR (гироскоп: `Mahony.h`, `MotionSample.h`, сброс слота DSU по MAC в
  `integrate_motion`) — желательно, чтобы PR сливались без конфликтов.

## 6. Наш черновик (гипотеза)

- В `ConcurrentQueue` добавить извлечение с таймаутом (`wait_for` на имеющемся `m_condVar`).
- `writer_thread` ждёт задание не дольше ~1 с. По таймауту: для каждого слота, который запрашивали (новый флаг,
  ставится в `request_pad_data(index)`), и от которого нет пакета дольше ~1 с (`ControllerState::last_update`),
  повторить запрос данных.
- Объём ~25 строк в 3 файлах. Пока сервера нет — один маленький UDP-пакет в секунду на слот.
