# Cemu: оценка смещения гироскопа уводит прицел — постановка задачи для PR

> Документ для независимой оценки. Нужно не «одобрить готовое», а найти лучшее решение и подводные камни,
> которые мы могли пропустить. Всё, что ниже помечено как «наш вариант», — черновик, его можно и нужно критиковать.

---

## 1. Контекст

**Cemu** — эмулятор Wii U (github.com/cemu-project/Cemu, C++). Последний стабильный релиз — v2.6 (6 февраля 2025),
основная ветка активно развивается.

Wii U GamePad имеет гироскоп и акселерометр; игры (в нашем случае *The Legend of Zelda: Breath of the Wild*,
прицеливание из лука) читают их через VPAD API. Cemu берёт движение от внешних источников:

- **DSU / Cemuhook** (`src/input/api/DSU/DSUControllerProvider.cpp`) — UDP-протокол. Источники: DS4Windows,
  BetterJoy, приложения для телефона (например, PhoneGyro — наш проект), самодельные контроллеры. Частота
  60–1000 Гц, у каждого пакета метка времени в микросекундах.
- **SDL** (`src/input/api/SDL/SDLControllerProvider.cpp`) — DualSense, DualShock 4, Switch Pro, Joy-Con и др.
- Wiimote (`WiimoteControllerProvider`) объявляет `WiiUMotionHandler`, но не кормит его (MotionPlus идёт своим путём) —
  изменение его не затрагивает.

Мы — авторы PhoneGyro (телефон или USB-контроллер на Arduino + MPU-6050 → DSU). Наш источник на выходе даёт уже
откалиброванные скорости, в покое — ровные нули.

## 2. Как устроен путь движения в Cemu

### 2.1. Приём (DSU)

```cpp
// DSUControllerProvider::integrate_motion — вызывается для КАЖДОГО принятого пакета
const uint64 ts = data_response.GetMotionTimestamp();
if (ts <= m_last_motion_timestamp[index]) { /* >10 s в прошлом → сброс метки */ return; }
const uint64 elapsedTime = ts - m_last_motion_timestamp[index];
m_last_motion_timestamp[index] = ts;
const double elapsedTimeD = (double)elapsedTime / 1000000.0;
m_motion_handler[index].processMotionSample((float)elapsedTimeD,
    gyro.x * 0.0174533f, gyro.y * 0.0174533f, gyro.z * 0.0174533f,   // °/с → рад/с
    acc.x, -acc.y, -acc.z);                                           // g
m_state[index].motion_sample = m_motion_handler[index].getMotionSample();
```

### 2.2. Приём (SDL)

Гироскоп в рад/с (как отдаёт SDL3), акселерометр делится на 9.81 → в g, `deltaTime` — из меток времени сенсора
(нс → с), ограничено 1.0 с. Тот же `processMotionSample`.

### 2.3. `WiiUMotionHandler` (`src/input/motion/MotionHandler.h`)

```cpp
void processMotionSample(float deltaTime, float gx, float gy, float gz, float accx, float accy, float accz)
{
    m_gyro = {gx, gy, gz}; m_prevAcc = m_acc; m_acc = {accx, accy, accz};
    m_imu.updateIMU(deltaTime, gx, gy, gz, accx, accy, accz);
    m_orientation = ... // yaw/pitch/roll из кватерниона
}
MotionSample getMotionSample()
{
    // gyroDebiased = m_gyro - bias  → уходит в игру как VPAD gyroChange
    return MotionSample(m_acc, accAcceleration, gyroDebiased, m_orientation, quaternion);
}
```

В игру уходят **три** величины, и все зависят от смещения (bias):
1. `gyroChange` — мгновенная скорость `m_gyro − bias` (через `MotionSample::getVPADGyroChange`);
2. `gyroOrientation` — углы из кватерниона фильтра;
3. `dir` — матрица ориентации из того же кватерниона.

### 2.4. Фильтр (`src/input/motion/Mahony.h`, класс `MahonySensorFusion`) — не менялся по сути с 2022 г.

```cpp
void updateIMU(float deltaTime, float gx, float gy, float gz, float ax, float ay, float az)
{
    Vector3f av(ax, ay, az);
    Vector3f gv(gx, gy, gz);
    if (deltaTime > 0.2f)
        deltaTime = 0.2f;
    updateGyroBias(gx, gy, gz);
    gv -= m_gyroBias;
    // ignore small angles to avoid drift due to bias (especially on yaw)
    if (fabs(gv.x) < 0.015f) gv.x = 0.0f;   // ~0.86 °/с, по каждой оси
    if (fabs(gv.y) < 0.015f) gv.y = 0.0f;
    if (fabs(gv.z) < 0.015f) gv.z = 0.0f;
    if (acc != 0) { av.Normalize(); grav = m_imuQ.GetVectorZ() * 0.5f; gv -= grav.Cross(av); } // только P-коррекция по гравитации
    gv.Scale(0.5f * deltaTime);
    m_imuQ += m_imuQ * Quaternionf(0, gv);
    m_imuQ.NormalizeXYZW();
    updateOrientationAngles();
}

void updateGyroBias(float gx, float gy, float gz)
{
    // dont let actual movement influence the bias
    // but be careful about setting this too low, there are controllers out there with really bad bias
    // (my Switch Pro had -0.0933 0.0619 0.0179 in resting state)
    if (fabs(gx) >= 0.35f || fabs(gy) >= 0.35f || fabs(gz) >= 0.35f)
        return;
    m_gyroTotalSum += {gx, gy, gz};
    m_gyroTotalSampleCount++;
    if (m_gyroTotalSampleCount >= 200)
        m_gyroBias = m_gyroTotalSum / m_gyroTotalSampleCount;   // среднее за ВСЁ время жизни, без забывания
}
```

Смещение одно на `WiiUMotionHandler`; тот живёт столько же, сколько провайдер (для DSU — массив по слотам).
Сброса нет: смена устройства на том же слоте DSU наследует старое смещение.

### 2.5. `getVPADGyroChange` (`MotionSample.h`) — второй баг, уже исправлен отдельно (PR 1)

Фильтр шума 0.012 рад/с проверял выходной массив до записи в него и потом перезаписывал его — порог никогда не
работал. PR 1 (готов, отдельный) применяет порог к `m_gyro` до перевода единиц. **Наш дрейф PR 1 не лечит:**
накопленное смещение (0.83 °/с = 0.0145 рад/с) выше порога 0.012.

## 3. Баг

**Симптом.** В BotW прицел лука медленно и постоянно уходит в сторону, даже когда геймпад неподвижен и источник
шлёт точные нули. Со временем игры становится хуже. Помогает только перезапуск Cemu.

**Механизм.** Оценка смещения — среднее всех «медленных» образцов (все оси < 0.35 рад/с ≈ 20 °/с) за всё время.
Прицеливание асимметрично: медленно ведём в одну сторону (попадает в среднее), быстро возвращаемся (≥ 20 °/с,
отбрасывается). Среднее смещается в сторону медленного движения и никогда не забывается. Дальше:
- `gyroChange = m_gyro − bias`: в покое игра получает `−bias` каждый кадр (порога нет, см. 2.5);
- кватернион: `−bias` отрезается порогом 0.015, пока |bias| < 0.86 °/с; больше — дрейфует и ориентация.

Тилт (pitch/roll) частично спасает P-коррекция по гравитации; рыскание (yaw) ничем не корректируется — поэтому
уходит именно горизонталь.

**Доказательства (наши замеры):**
- Захват пакетов DSU на проводе в момент дрейфа: 100 % скоростей — точные нули.
- Реплей алгоритма `updateGyroBias` на пакетах, которые мы отправили: после одного медленного поворота +0.832 °/с
  по оси Y — ровно то, куда уходил прицел.
- Перезапуск Cemu (сброс суммы) убирает дрейф; отключение нашего источника — нет (Cemu держит последний образец и
  смещение).
- Симуляция на настоящем `Mahony.h` (g++, те же заголовки), 10 минут «лука» (4 с прицел 10 °/с, 0.5 с возврат
  −80 °/с, 3 с удержание): смещение +6.4 °/с, прицел уходит на 63° за 10 с покоя. На 60/200/1000 Гц одинаково.

**Почему «только у Cemu»** (по аудиту другого нашего агента, мы сами не перепроверяли):
Ryujinx передаёт гироскоп как есть с порогом; Yuzu/Suyu/Citron — EMA 0.9999 только когда «не движется»
(и |a| в 0.9–1.1 g); Dolphin перезапускает калибровку при любом движении и имеет выключатель; Citra — сырые данные.

## 4. Ограничения на решение

1. **Политика Cemu**: код должен быть написан человеком; у мейнтейнеров мало времени на ревью. Значит: маленький,
   понятный, хорошо обоснованный diff. Желательно в пределах `Mahony.h`.
2. **Контроллеры с большим собственным смещением** обязаны работать: автор фильтра прямо пишет про Switch Pro с
   −0.0933/0.0619/0.0179 рад/с (до 5.3 °/с). Регрессия для них — почти гарантированный отказ в PR.
3. **Частота 60–1000 Гц** и неравномерные интервалы — логика должна быть по времени, а не по числу образцов
   (сейчас «200 образцов» — это 3.3 с на 60 Гц и 0.2 с на 1000 Гц).
4. **Источники без акселерометра** (DSU шлёт нули) — не должны ломаться.
5. **Единицы**: гироскоп рад/с, акселерометр g, `deltaTime` с — одинаково для DSU и SDL (проверено по коду).
6. Смещение используется и в кватернионе, и в `gyroChange` — решение должно быть корректно для обоих.
7. Остаточная ошибка после решения должна быть ниже порогов 0.012 (gyroChange, после PR 1) и 0.015 рад/с
   (кватернион), тогда в покое игра видит ровный ноль.
8. Температурный дрейф смещения (медленный, минуты) желательно отслеживать.
9. Не ломать источники, которые уже калибруют сами (PhoneGyro, DS4Windows, BetterJoy, SDL с заводской калибровкой
   для DualSense/DS4 — насколько мы знаем; не проверено для всех).

## 6. Принципиальная трудность

По одному гироскопу **нельзя отличить постоянное смещение от плавного вращения с постоянной скоростью**.
Акселерометр видит вращение только вокруг осей, не совпадающих с гравитацией; поворот по рысканию (ровно то, что
делает прицел) акселерометр не видит. Остаются косвенные признаки:
- **дрожь**: рука всегда дрожит (0.3–2 °/с СКО), стол — нет (шум датчика ~0.1–0.2 °/с);
- **длительность**: смещение постоянно всегда, плавное движение человека длится секунды;
- **скачок**: настоящее смещение меняется медленно (температура), оценка «прыгнуть» на несколько °/с не должна
  без сильных доказательств.

Худший реалистичный случай для любого «детектора покоя» — геймпад лежит на колене/подлокотнике и игрок плавно
ведёт прицел без дрожи.

## 7. Рассмотренные варианты и результаты симуляции

Симуляция (Python, логика 1:1 с C++-черновиками; основные выводы подтверждены на настоящем `Mahony.h` в g++).
Метрика — худшая по осям ошибка смещения в конце сценария, °/с (= скорость дрейфа прицела в покое).

**Варианты:**
- **OLD** — текущий `Mahony.h`.
- **draft** — наш первый черновик: «покой» = каждая выборка отклоняется от короткого среднего (EMA 0.25 с) меньше
  0.03 рад/с и акселерометр меньше 0.03 g, |a| ≈ 1 g; после 1 с покоя первое смещение берётся как есть, дальше —
  плавное следование (τ = 2–5 с).
- **V3** — текущий кандидат:
  - покой = **дисперсия** (EMA 0.25 с) гироскопа < (0.01 рад/с)² и акселерометра < (0.02 g)² по каждой оси,
    |среднее| < 0.25 рад/с; проверку |a| ≈ 1 g убрали (ломает источники без акселерометра и ничего не добавляет);
  - первое смещение — после 1 с покоя, как есть;
  - дальше: если новое среднее близко к текущему смещению (< 0.01 рад/с ≈ 0.57 °/с) — 1 с покоя и плавное
    следование (τ = 3 с); если далеко — нужно 3 с непрерывного покоя, тогда берётся сразу («защита от скачка»);
  - всё по времени (`deltaTime`), не по числу образцов.
- **V3+fall** — V3, но **до первого покоя** работает старый алгоритм (поведение как сейчас), после — V3.

  лучше отделяет стол от руки (раздел 5).
- **Нерешённый конфликт** — геймпад, который ни разу не положили:
  - V3: откалиброванные источники идеальны, а контроллер с большим заводским смещением дрейфует на всё своё
    смещение (Switch Pro — 5.3 °/с), пока его не положат хотя бы на 1 с;
  - V3+fall: никому не хуже, чем сейчас, но и не лучше, пока геймпад не положили.
- Очень медленные плавные повороты (0.5 °/с) дают остаток ~0.46 °/с — ниже обоих порогов (0.69 и 0.86 °/с),
  то есть в игре не виден, но это на грани.

## 8. Черновик V3 (псевдокод, для обсуждения)

```cpp
// state: m_gyroAverage[3], m_gyroVariance[3], m_accAverage[3], m_accVariance[3],
//        m_stillTime, m_gyroBias[3], m_hasGyroBias (+ опционально старые сумма/счётчик для fallback)
void updateGyroBias(float dt, const float g[3], const float a[3])
{
    const float k = std::min(dt / 0.25f, 1.0f);             // EMA ~0.25 s, по времени
    bool still = true;
    for (i in 0..2) {                                         // первая выборка: average = sample, variance = 0
        m_gyroAverage[i]  += (g[i] - m_gyroAverage[i]) * k;
        m_gyroVariance[i] += (sq(g[i] - m_gyroAverage[i]) - m_gyroVariance[i]) * k;
        m_accAverage[i]   += (a[i] - m_accAverage[i]) * k;
        m_accVariance[i]  += (sq(a[i] - m_accAverage[i]) - m_accVariance[i]) * k;
        if (m_gyroVariance[i] >= sq(0.01f) || m_accVariance[i] >= sq(0.02f) || fabs(m_gyroAverage[i]) >= 0.25f)
            still = false;
    }
    if (!still) { m_stillTime = 0; return; }
    m_stillTime += dt;
    const bool jump = m_hasGyroBias && maxAbsDiff(m_gyroAverage, m_gyroBias) >= 0.01f;
    if (m_stillTime < (jump ? 3.0f : 1.0f)) return;
    const float kb = (jump || !m_hasGyroBias) ? 1.0f : std::min(dt / 3.0f, 1.0f);
    m_gyroBias += (m_gyroAverage - m_gyroBias) * kb;
    m_hasGyroBias = true;
}
```

Побочное полезное свойство: EMA взвешены по времени, поэтому пакеты с крошечным `dt` почти не влияют на оценки.
(Для контекста: в PhoneGyro сейчас стоит временный обходной путь для текущего Cemu — служебные пакеты длительностью
1 мкс, которые обнуляют сумму старого алгоритма. На исправленном Cemu они безвредны: вклад каждого в EMA ~4·10⁻⁶.)

## 9. Открытые вопросы — где нужно ваше мнение

1. **Что делать до первого покоя?** «Смещение 0» (как Dolphin/Yuzu, идеально для откалиброванных источников, но
   регрессия для «некалиброванного Switch Pro в руках с самого старта») или «старый алгоритм до первого покоя»
   (никому не хуже, но баг остаётся у тех, кто никогда не кладёт геймпад). Есть ли третий путь?
   Например: мягкий «ручной» уровень с очень медленной EMA (как у Yuzu, τ ~ минута) только для больших смещений?
   Использовать `m_hasGyroBias`-состояние, чтобы включать старое поведение только если «видно большое постоянное
   смещение»? Как отличить его от асимметричного прицеливания?
2. **Пороги.** 0.01 рад/с СКО гироскопа и 0.02 g акселерометра выбраны по нашим MPU-6050 и телефонам. Хватит ли
   для шумных контроллеров (Joy-Con, DualSense, Switch Pro)? Не станет ли «покой» недостижимым для них? Стоит ли
