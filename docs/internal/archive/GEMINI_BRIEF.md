# Бриф для Gemini: рефакторинг фронта PhoneGyro + финальный README

Ты работаешь над PhoneGyro — приложением на Go + Wails v2 для Windows, которое превращает
смартфон (страница в браузере) или USB-контроллер (Arduino Nano + MPU-6050) в источник
движения Cemuhook DSU для эмуляторов. Проект рабочий и протестирован вживую. **Главная
задача — не сломать то, что работает.**

---

## 0. Жёсткие правила (нарушение = откат всей работы)

1. Работай **только в ветке `refactor/frontend`**. Никогда не коммить в `main` и `dev`, никогда не делай push в `main`.
2. Точка отката — тег **`pre-gemini`**. Если что-то пошло не так: `git reset --hard pre-gemini` на своей ветке.
3. **Рефакторинг не меняет поведение.** Ни одна кнопка, текст, анимация, звук или порядок действий не должны измениться, кроме явно оговорённых багфиксов (раздел 3).
4. **Маленькие шаги, один шаг = один коммит.** После каждого шага приложение собирается и запускается (раздел 4). Никаких «переписал 5000 строк одним коммитом».
5. **Не трогай Go-код** (`gui/*.go`, `pkg/`), `web/index.html` (страница телефона), `docs/guide.*.md` и прошивку — без прямой просьбы владельца.
6. **Не удаляй функции, ключи i18n, id элементов и CSS-классы**, пока не доказал поиском (`grep`), что они нигде не используются — ни в HTML, ни в JS, ни в Go, ни в `pkg/i18n/locales/*.json`.
7. В сообщениях коммитов **не добавляй строку `Co-Authored-By`** (владелец просил так не делать).
8. Если не уверен — **остановись и спроси**, а не угадывай.

## 1. Как устроен фронт (прочитай до начала работы)

```
gui/frontend/src/
  index.html      ~11 500 строк: разметка главного окна + ОДИН большой <script> (с ~2415 строки)
  main.css        ~8 300 строк: все стили главного окна
  livedebug.html  ~4 600 строк: отдельное окно "Статистика & 3D", свой <script>, СВОЙ словарь переводов DICTIONARY
  assets/         three.min.js, GLTFLoader.js, модели
  wailsjs/        АВТОГЕНЕРИРУЕМЫЕ привязки Go -> JS. Не редактировать руками.
  main.js         мусор из шаблона Wails, не подключён (можно удалить, проверив grep)
```

Важные особенности, на которых легко всё сломать:

- **Весь JS главного окна — один классический `<script>`**. Объекты-менеджеры объявлены на верхнем уровне через `const` (`AppState`, `ProfileManager`, `RecenterManager`, `FirstCenterGate`, `SettingsManager`, `CalibrationWizard`, `AppleSelect`, `AppleCloseDialog`, `ProfileDeleteDialog`, `SetupWizard`, `HelpManager`, `WelcomeManager`, `Scene3D`, `TuningBench` и др.) и обращаются друг к другу по имени. Если выносишь их в отдельные файлы — используй **обычные `<script src>` (не `type="module"`)** и сохрани **порядок подключения**: верхнеуровневые `const` из классических скриптов видны друг другу только если объявлены до момента вызова. Модули ES сломают эту видимость.
- Связь с Go: `window.go.main.App.<Метод>(...)` и события `window.runtime.EventsOn(...)`. Имена методов и событий менять нельзя.
- **Переводы**: тексты берутся из `pkg/i18n/locales/ru.json` и `en.json` через `I18n.t('раздел.ключ')` и атрибуты `data-i18n`, `data-i18n-title`, `data-i18n-tip`. У `livedebug.html` свой встроенный словарь `DICTIONARY` (ru/en) — это отдельная система.
- **`AppleSelect`** подменяет свойство `select.value` у нативных `<select>` и рисует свою выпадашку в `document.body`. Не заменяй нативные select'ы на что-то другое.
- **`.profile-dropdown-item *` имеет `pointer-events: none`**, а крестик удаления профиля явно возвращает `pointer-events: auto`. Порядок и специфичность этих правил важны.
- **`RecenterManager.close()`** в обязательном режиме (первое подключение) намеренно ничего не делает; закрывает только `close(true)`.
- **Live Debug** внутри приложения получает данные через Go-мост (`livedebug:telemetry`), а собственный WebSocket страницы игнорирует сообщения, если мост активен (`wailsBridgeRegistered`). Не убирай эту проверку — иначе каждый кадр обрабатывается дважды.
- Всё, что в `window.*`, может вызываться из Go или из инлайновых `onclick` — ищи использования перед переименованием.

## 2. План рефакторинга (по порядку, каждый пункт — отдельный коммит или серия)

1. **Инвентаризация.** Составь список всех верхнеуровневых объектов/функций скрипта `index.html` с диапазонами строк и зависимостями (кто кого вызывает). Положи его в `docs/internal/FRONTEND_MAP.md`. Кода не меняй.
2. **Вынос JS в файлы без изменений.** Перенеси содержимое большого `<script>` в `gui/frontend/src/js/app.js` ОДИН В ОДИН и подключи его `<script src="js/app.js"></script>` на то же место. Собери, проверь (раздел 4).
3. **Разбиение по менеджерам.** По одному объекту за коммит: `js/profile-manager.js`, `js/recenter.js`, `js/settings.js`, `js/calibration.js`, `js/apple-select.js` и т.д. Порядок `<script src>` = порядок объявления в исходном файле.
4. **CSS.** Так же: сначала вынос без изменений, потом разбиение `main.css` на файлы по разделам (`css/base.css`, `css/profiles.css`, `css/dialogs.css`, `css/settings.css`, ...), подключаемые в том же порядке. Порядок правил влияет на результат — не переставляй.
5. **Удаление мёртвого кода** — только с доказательством (grep по всему репозиторию), отдельными коммитами, в сообщении перечисли, что удалено и почему это не используется.
6. **`livedebug.html`** — тем же способом, но отдельной серией после главного окна.

Не надо: переходить на фреймворк (React/Vue/Svelte), бандлер, TypeScript, менять дизайн. Это рефакторинг, а не переписывание.

## 3. Визуальные баги («рендерится квадратами» и т.п.)

Сначала **воспроизведение, потом правка**. Для каждого бага запиши: где (окно, экран), что видно, как вызвать, стабильно ли. Не чини вслепую.

Вероятные причины, которые стоит проверить (гипотезы, не факты):
- `backdrop-filter: blur(...)` на больших или анимируемых слоях в WebView2 — может давать артефакты блоками при композитинге;
- одновременные CSS-анимации `transform/opacity` поверх `<canvas>` three.js;
- canvas three.js, у которого размер буфера не совпадает с CSS-размером после ресайза/масштабирования (`zoom` интерфейса через FontScaleManager);
- `will-change` на множестве элементов.

Каждый фикс — отдельный коммит с описанием бага и причины.

## 4. Проверка после КАЖДОГО шага

1. Синтаксис: `node --check` для каждого вынесенного `.js`.
2. Go-тесты не должны сломаться: `cd gui && go test ./...` и `go test ./...` в корне.
3. Сборка: `cd gui && wails build -tags native_webview2loader -o PhoneGyro.exe` (результат — `gui/build/bin/PhoneGyro.exe`). Если сборка перегенерирует `wailsjs/` — это нормально.
4. Запуск и ручной прогон (или попроси владельца):
   - главное окно открывается, переключение RU/EN, светлая/тёмная тема;
   - выпадашка профилей, выбор профиля, крестик удаления → модалка;
   - «Центрировать», окно первого подключения (обязательное, без крестика);
   - Настройки: оба порога дрожи, описания под пунктами списка, автосохранение;
   - мастер калибровки открывается и листается;
   - Live Debug открывается, 3D-вид, запись CSV, секция «Протокол USB» в режиме USB;
   - консоль DevTools без новых ошибок.

## 5. Финальный README и Quick Start

Файлы: `README.md` (EN), `docs/README_RU.md` (RU). Подробные руководства `docs/guide.en.md` / `docs/guide.ru.md` уже обновлены — **на них ссылайся, не переписывай их**.

Правила:
- **Только факты, которые подтверждаются кодом или переводами** (`pkg/i18n/locales/*.json`, `gui/*.go`). Не выдумывай функции, цифры, поддерживаемые эмуляторы и «бенчмарки».
- Названия кнопок бери дословно из i18n (EN: «Calibrate», «Recenter», «Initial Setup», «Stats & 3D View»; RU: «Калибровать», «Центрировать», «Начальная настройка», «Статистика & 3D просмотр»).
- Тон — дружелюбный и сухой, без маркетинговых превосходных степеней («лучший», «единственный», «революционный»).
- В Quick Start калибровка должна быть явно помечена как обязательный шаг с объяснением «без неё прицел двигается не по той оси».
- RU и EN — одинаковые по содержанию.
- Места под логотип, ссылку на видео и гифку оставь как явные заглушки (`<!-- TODO: logo -->`), не вставляй чужие картинки.
- Сохрани разделы про безопасность/антивирусы и сборку из исходников.
