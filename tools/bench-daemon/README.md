# PhoneGyro bench

Замер производительности UI: после изменения запусти, получи числа, сравни с прошлым отчётом. Числа честные, если отчёт не помечен `INVALID` и нет предупреждений в шапке.

Цель — **60 fps на стенде 2 (Intel HD)**. Стенд 1 (RTX 3070) показывает потолок, а не цель.

## Запуск

```cmd
bench.cmd --native --runs 3            :: настоящий PhoneGyro.exe — числа, которые важны (только Windows)
bench.cmd --native --stress --runs 3   :: длиннее и тяжелее
bench.cmd --browser --runs 3           :: только фронтенд в Chrome/Edge с мок-бэкендом
node tools/bench-daemon/compare.mjs reports\before.json reports\after.json
```

- Нужен Node.js 22+. Сторонние пакеты не нужны.
- `PhoneGyro.exe` ищется так: рядом с `bench.cmd`, затем в `PHONEGYRO_BIN`, затем в `gui/build/bin`.
- Отчёты пишутся в `reports/` рядом с `bench.cmd` в двух видах: `.txt` для чтения и `.json` со всеми сырыми прогонами.
- Коды выхода:
  - `0` — всё валидно и в цели;
  - `1` — этап не уложился в цель;
  - `3` — этап `INVALID`, его числа ничего не значат;
  - `2` — упал сам бенч.
- `compare.mjs` возвращает `1`, если что-то стало хуже сверх шума.

## Как получить сравнимые числа

1. **Только `--native` на целевом стенде.** Браузерный режим в headless рисует WebGL программно (SwiftShader) и в шапке об этом предупреждает. Он годится, чтобы найти лишнюю работу JS, стилей и layout, но не для fps на реальном GPU.
2. **`--runs 3` и больше.** Каждый прогон — новый запуск приложения. В отчёте медиана и (мин–макс). `compare.mjs` засчитывает изменение, только если оно больше разброса обоих отчётов.
3. **Одинаковые условия.** Тот же стенд, то же разрешение и частота экрана, работа от сети (на батарее в шапке будет WARNING). Окно не трогать, других тяжёлых программ не запускать: поле `other load %` показывает фоновую нагрузку. `compare.mjs` откажется сравнивать отчёты с разных CPU, GPU или частот экрана.
4. **A/B фронтенда без сборки:** `--browser --frontend <worktree>\gui\frontend\src` — тот же бенч на другой версии фронтенда.
5. **Сначала коммит, потом замер.** В шапке пишутся ветка и коммит, а также флаг `+uncommitted gui changes`.

## Что делает прогон

Нативный режим запускает `PhoneGyro.exe --bench` с отладкой WebView2.
- Существующий PhoneGyro бенч закрывает, потому что приложение допускает только один экземпляр.
- `APPDATA` указывает на временную копию данных пользователя (настройки, профили, сертификаты). Бенч ничего не пишет в настоящие данные, а WebView2 каждый раз стартует с чистого профиля. Флаг `--real-data` отключает изоляцию.
- Калибровку и `GetState` отвечает бенч, а не бэкенд: устройства нет, профили не записываются. Всё остальное — настоящий Go и WebView2.
- События идут в страницу тем же путём, что из Go (`wails.EventsNotify`, JSON).

| Этап | Что происходит |
|---|---|
| boot | Перезагрузка страницы, замер с первого кадра до ухода сплэша. Тайминги DOMContentLoaded, load, first paint, splash gone. Вердикта нет (INFO) |
| connect | Подключение устройства |
| calibrate | Мастер калибровки кликами: 4 шага, 3D-сцена, закрытие. Проверяется, что все 4 шага пройдены |
| motion | Кватернион 60 Гц и стейт 15 Гц, как шлёт Go, 2 DSU-клиента |
| tuning | Настройки, разворачивается график отклика, `tuning:frame` 60 Гц |
| disconnect | Обрыв связи и переподключение |
| pages | Переключение экранов кликами: settings, stats, docs, games, connect |
| reflow | Смена темы (`theme-sync`) и масштаба (`font-scale-sync`) |
| idle | Подключено и неподвижно: тот же стейт 15 Гц. Правило 0 — приложение не должно ничего делать. Вердикт: app rAF/s = 0 и layout ≤ 0.5 мс/с. Скрипт и стили только показаны: в них входят рекордер бенча (~5 мс/с) и, в headless, CSS-анимации на главном потоке |

## Числа

- **fps, p50/p95/p99/max** — интервалы между кадрами по rAF-рекордеру.
- **slow %** — доля кадров дольше 20.8 мс (1.25 × 16.7). Это кадры, где 60 fps не удержан, при любой частоте экрана. Именно по нему ставится вердикт: PASS, если ≤ 1 %.
- **drop %** — доля интервалов обновления экрана без кадра. Частота экрана измеряется в начале прогона.
- **app rAF/s** — сколько раз в секунду приложение само просит `requestAnimationFrame`, без цикла рекордера. В `idle` должно быть 0.
- **script / style / layout / task ms/s** — время главного потока на секунду этапа (CDP Performance).
- **LoAF ms** и **long frame** — длинные кадры (Long Animation Frames) со скриптами, которые их вызвали: функция, файл, позиция.
- **comp drop %** — доля кадров, которые компоситор выбросил или показал частично (из трассировки Chrome). Видит задержки растеризации и GPU, которых rAF-рекордер не видит: rAF меряет только главный поток. Для заставки и анимаций это главное число.
- **raster ms/s, paint ms** — время растеризации и отрисовки.
- **layers Mpx** — пиковая площадь отрисованных композитных слоёв за загрузку в миллионах device-пикселей (×4 байта = видеопамять). Не зависит от GPU, поэтому сравнимо между стендами; на встройке это память и смешивание на каждом кадре.
- **heap MB** — JS-куча после принудительного GC. **DOM**, **listeners** — для поиска утечек.
- **CPU cores** — CPU всего дерева процессов (PhoneGyro.exe и все процессы WebView2) за секунду; 1.0 = одно ядро занято. Разбивка: **renderer**, **GPU proc**, **Go**. **RAM MB** — working set всего дерева. Только `--native`.
- **other load %** — нагрузка остальной машины во время этапа. Большая — значит прогон шумный.

## Когда этап INVALID

Этап получает `INVALID`, если:
- сценарий не дошёл до заявленного состояния (например, калибровка прошла не все 4 шага);
- окно было скрыто или без фокуса;
- в нативном режиме передний план занимало другое приложение;
- записано меньше 10 кадров.

Числа такого этапа в медиану не идут. Причина пишется в отчёте.
